# Handoff PR-069 · Validación real acotada del operador (redgifs) + fix de estructura

**Feature**: `specs/008-redgifs-adapter` · **Depende de**: PR-067 `DONE` + habilitación
humana en BD (ejecutada por el operador el 2026-08-20: `update public.sources
set enabled=true where name='redgifs';`).

## Resumen

Backfill real acotado ejecutado contra `api.redgifs.com` sobre los dos nichos
de validación de la spec, con el CLI/pipeline reales (sin mocks). Se encontró
y corrigió **un bug real** en `discover()` durante la primera ejecución (ver
abajo); tras el fix, el flujo completo funcionó de punta a punta con datos
reales: 101 vídeos indexados, 202 frames con embedding y pHash, 0 duplicados
en un INCREMENTAL posterior, 0 descargas de mp4.

## Bug encontrado y corregido

**Síntoma**: el primer `backfill --source redgifs --section /niches/homemade
--max-videos 50` encoló el job DISCOVER, pero quedó `failed` tras 3 intentos:

```
RedgifsParseError: la página trae 100 IDs con limit=50; limit debe ser >= tamaño
de página (truncación no soportada)
```

**Causa**: `discover()` pedía siempre `count=100` a la API
(`_PAGE_COUNT` fijo), ignorando el `limit` que pasa el pipeline (por defecto
`XTRACE_CRAWLER_BACKFILL_DEFAULT_LIMIT=50` cuando el operador no pasa
`--limit`). La API devolvía 100 IDs, y el guard de truncación (correcto en sí
mismo — nunca debe descartar IDs en silencio) los rechazaba porque 100 > 50.

**Fix**: `services/crawler/xtrace_crawler/adapters/redgifs.py` — `count` ahora
sigue a `limit` (`count = min(limit, 100)`, con 100 como tope máximo aceptado
por la API, sin cambios ahí), en vez de un valor fijo. Este era exactamente el
propósito de PR-069 (validar contra la API real antes de confiar en la
prospección): el bug no aparecía en los 45 tests de PR-066 porque todos usaban
`limit=100` (coincidiendo por casualidad con el fijo) salvo el test de
truncación (`limit=1`, que sigue fallando correctamente porque la página trae
más IDs de los pedidos).

**Tests de regresión añadidos** (`tests/unit/test_redgifs_adapter.py`):
- `test_discover_usa_count_igual_al_limit_cuando_limit_menor_que_100` — con
  `limit=50`, la query usa `count=50` (el escenario real que falló).
- `test_discover_usa_count_100_como_tope_maximo_con_limit_mayor` — con
  `limit=500`, la query sigue acotada a `count=100` (máximo de la API).

Total: 46 tests en `test_redgifs_adapter.py` (44 de PR-066 + 2 de esta
regresión), todos en verde.

## Validación de la estructura real de la API (antes del backfill, con `curl`)

Se confirmó con peticiones `curl` directas (sin tocar el adapter) que la
estructura observada en la prospección de 2026-08-19 sigue vigente:

- `GET /v2/auth/temporary` → `{"token": "<jwt>", ...}` ✓
- `GET /v2/niches/homemade/gifs?order=new&count=2&page=1` → envelope
  `{gifs, page:1, pages:33059, total:66118, ...}` (con `count=2`; confirma que
  `pages = ceil(total/count)`, paridad con la fórmula asumida) ✓
- Objeto gif del listado: `id`, `description`, `createDate`, `duration`,
  `tags`, `hasAudio`, `type`, `urls.{thumbnail,poster,sd,hd,silent,html}` ✓
- `GET /v2/gifs/<id>` → `{"gif": {...}, "user": {...}, "niches": [...]}` ✓
- `GET /v2/gifs/<id-inexistente>` → `404 {"error":{"code":"GifNotFound",...}}` ✓
- `/niches/real-cellphone-clips` → nicho válido, `total=3671` (JSON real
  descartado tras la comprobación; nunca commiteado, SEC-004; capturas en

**Verificación directa en BD (Supabase local)**:

```sql
-- 0 duplicados por (source_id, external_id):
select external_id, count(*) from videos v join sources s on s.id=v.source_id
where s.name='redgifs' group by external_id having count(*) > 1;
-- → 0 filas

select count(*) from videos v join sources s on s.id=v.source_id where s.name='redgifs';
-- → 101

select source_kind, timestamp_ms, count(*) from frames f
join videos v on v.id=f.video_id join sources s on s.id=v.source_id
where s.name='redgifs' group by source_kind, timestamp_ms;
-- → source_kind='video_frame', timestamp_ms=NULL, count=202  (101×2: thumbnail+poster)

select count(*), count(embedding), count(phash) from frames f
join videos v on v.id=f.video_id join sources s on s.id=v.source_id where s.name='redgifs';
-- → 202, 202, 202  (todos con embedding fake + pHash)
```

## Criterios de aceptación verificados (evidencia real, no solo fixtures)

- **SC-002** (backfill real produce vídeos/frames/embeddings consultables):
  ✓ 101 vídeos, 202 frames, 202 embeddings/pHash, consultados directamente en
  Postgres.
- **SC-003** (INCREMENTAL sin duplicados): ✓ 0 filas con `external_id`
  repetido; el segundo INCREMENTAL solo añadió 3 vídeos genuinamente nuevos
  (feed `order=new` avanzó entre ejecuciones).
- **SC-004** (0 descargas de mp4): ✓ por construcción — `get_visual_assets`
  solo lee `thumbnail_url`/`storyboard_urls[0]` (poster) del `VideoSource` ya
  normalizado; el código nunca lee `urls.sd/hd/silent`. 202 frames = 2×101
  (nunca más, lo que confirmaría un tercer asset filtrándose).
- **SC-005** (rate limit respetado): ✓ logs de cada pasada mostraron
  `waits=1 wait_ms≈1000-1100` (espaciado del limiter activo); nunca 429 de la
  API real en toda la sesión.
- **NFR-004**: ✓ mismo punto anterior, medible en logs.
