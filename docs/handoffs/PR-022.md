# Handoff — PR-022

- **Proveedor y modelo usados** (obligatorio para auditar coste — p. ej. `provider: deepseek-official · model: deepseek-v4-flash`): `provider: deepseek-official · model: deepseek-v4-flash`
- **Resumen**: Rate limiter por fuente (`crawling/ratelimit.py`) con intervalo mínimo entre peticiones + ráfaga sostenida (token bucket) y jitter aditivo, puro e inyectable (reloj/sleeper/RNG) para tests deterministas sin dormir; sección rate en `config.py` (pydantic-settings) con defaults en código (`RateLimitSpec`) y overrides por env `XTRACE_CRAWLER_RATE_<SOURCE>_MIN_INTERVAL_MS` / `XTRACE_CRAWLER_RATE_<SOURCE>_MAX_RPS` (Decisión D5), sin tocar la estructura base de PR-019. Esperas medibles/contables vía `RateLimiter.stats` (SC-005).
- **Requisitos implementados**: FR-009 (rate limit configurable por adapter: defaults en código + override por env, con jitter) · SC-005 (0 violaciones medibles; tests con reloj fake) · D5 (contracts §4: nombres de env exactos) · NFR-004 (respeto al límite verificable en tests).
- **Archivos modificados** (solo `allowed_paths`; nada más):
  - Creados: `services/crawler/xtrace_crawler/crawling/ratelimit.py`, `services/crawler/tests/unit/test_ratelimit.py`.
  - Modificado: `services/crawler/xtrace_crawler/config.py` (sección rate añadida; campos base de PR-019 intactos).
  - Nota: `services/crawler/xtrace_crawler/crawling/__init__.py` se creó como marcador de paquete (estructura del plan §Project Structure); sin él el módulo del contrato no es parte de un paquete regular del estilo del repo.
- **Decisiones tomadas**:
  1. **Modelo**: `RateLimitSpec` (pydantic) con `min_interval_ms` (ge 0) y `max_rps` (gt 0) y defaults en código (1000 ms / 1.0 rps) → es el "spec de rate limit" del contrato; cuando PR-020 defina `AdapterManifest.rate_limit`, apuntará a este spec (o se alinea en converge).
  2. **Algoritmo**: intervalo mínimo + token bucket con capacidad de ráfaga = 1 segundo de tokens y refill continuo a `max_rps` tokens/s. `acquire()` espera `max(espera_intervalo, espera_bucket)` y devuelve los segundos esperados.
  3. **Jitter aditivo** (no "completo"): `uniform(0, wait * jitter_factor)` solo suma a la espera base, garantizando que **nunca** viola el intervalo mínimo (exigencia del contrato de tests). Factor por defecto 0.1, inyectable; `jitter_factor < 0` → `ValueError`.
  4. **Pureza**: `clock` (default `time.monotonic`), `sleeper` (default `asyncio.sleep` envuelto) y `rng` (default `random.Random()`) inyectables; `asyncio.Lock` serializa acquires concurrentes del mismo limiter.
  5. **Config**: fuente pydantic-settings propia (`_RateLimitEnvSource`, subclase de `PydanticBaseSettingsSource` — en pydantic-settings 2.15 el source se invoca sin argumentos y el ABC exige `get_field_value`), añadida en `settings_customise_sources` sin sustituir la cadena base. Los valores crudos del env los valida/coerciona pydantic en `RateLimitOverride` (env inválido → `ValidationError` al construir `Settings`). Override **parcial** posible (solo un campo).
  6. **Ámbito**: solo `crawling/ratelimit.py` + sección rate de `config.py`; sin tocar adapters (PR-020/021), jobs (PR-023/026) ni HTTP (PR-024). El limiter no loguea: expone `stats` (requests/waits/total_wait_seconds/last_wait_seconds) para que el worker (PR-027) y `stats` CLI (PR-032) logueen esperas por fuente.
- **Tests añadidos** (`tests/unit/test_ratelimit.py`, 9 tests, todos marcan el requisito que validan — constitución §3/§6):
  - FR-009/SC-005: intervalo mínimo nunca superado (reloj fake, sin dormir real).
  - FR-009/SC-005: ráfaga sostenida: 2 requests inmediatas (ráfaga = 1 s de tokens) y después 1 cada 0.5 s con `max_rps=2`; tiempo total exacto con reloj fake.
  - FR-009: jitter aditivo nunca viola el mínimo (gaps ≥ mínimo; sleeps en `[0.2, 0.3]` con factor 0.5 y seed fija).
  - SC-005: esperas medibles/contables (requests/waits/total/last exactos y consistentes con el reloj fake).
  - FR-009/D5: override por env gana al default; fuente sin env conserva defaults; override parcial respeta el otro campo; env inválido → `ValidationError`; vars no relacionadas no alteran la config (estructura base PR-019 intacta).

- **Limitaciones**:
  - `_RateLimitEnvSource` lee `os.environ` del proceso (no el `.env` de pydantic-settings); con `uv run` el `.env` se carga en el proceso antes, así que funciona en local igualmente. Documentado en el código.
  - La fuente custom no resuelve campos individuales (`get_field_value` devuelve vacío); solo aporta `rate_limits` completo — suficiente para este contrato.
  - No hay tests de concurrencia real del lock (el contrato no lo exige); el worker (PR-027) los aportará si aplica.
- **Riesgos**:
  - **Colisión futura de `RateLimitSpec`**: si PR-020 define el spec del manifest con otro nombre/campos, PR-030 deberá alinear (documentado en este handoff). Los nombres de env cumplen exactamente contracts §4.
  - pydantic-settings ≥ 2.15 cambió la firma de los sources (`__call__` sin argumentos); el código está verificado contra 2.15.0 (resuelta por `uv.lock`), no contra versiones anteriores.
- **Trabajo pendiente**: el worker (PR-027) debe instanciar un `RateLimiter` por fuente con `settings.rate_limit_for(source, manifest.rate_limit)` y loguear `stats`; PR-030 consume el limiter en el pipeline; PR-032 expone rate-limit waits en `stats` CLI.
