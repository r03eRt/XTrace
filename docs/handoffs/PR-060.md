# Handoff — PR-060

- **Proveedor y modelo usados**: `provider: deepseek-official · model: deepseek-v4-flash`
- **Resumen**: Fix del build de Next en CI (PR #10 de la Fase 3): `src/lib/api/xtrace.ts`
  importaba `{ env }` de `@/lib/env` (skeleton), y `env.ts` lanza en tiempo de evaluación si
  faltan `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` — ausentes en el job de
  calidad de CI → el prerender de `/buscar` fallaba. La búsqueda no necesita Supabase: el
  cliente ahora lee `process.env.NEXT_PUBLIC_XTRACE_API_URL` directamente con default
  `http://127.0.0.1:8000`, validando con `new URL()` y lanzando error claro **solo** si la env
  existe pero es inválida. `env.ts`, `src/lib/supabase/**` y la home quedan intactos.
- **Requisitos implementados**: SEC-006 (config por env, `.env.example` intacto con el default
  ya documentado), FR-009/010/011 + UX (cliente de búsqueda con comportamiento idéntico),
  spec 003 · contracts §6 (base URL default `http://127.0.0.1:8000`, solo local, sin auth).
- **Archivos modificados**:
  - `src/lib/api/xtrace.ts` (único cambio de código: sin import de `@/lib/env`; nueva
    `resolveApiBaseUrl()` + constante `API_BASE_URL`; `fetch` usa `API_BASE_URL`)
  - `docs/handoffs/PR-060.md` (este handoff)
  - No tocados: `src/lib/env.ts` (ya documenta el default `NEXT_PUBLIC_XTRACE_API_URL` en el
    schema sin cambiar la exigencia de Supabase — no hacía falta), `tests/unit/buscar-page
    .test.tsx` (ningún test quedó desalineado: la aserción de URL usa el default
    `http://127.0.0.1:8000/search`, que se mantiene; el bloque `vi.hoisted` de envs de
    Supabase queda inerte pero inofensivo), `.env.example`, home, supabase, servicios.
- **Decisiones tomadas**:
  - Resolución en constante de módulo (`const API_BASE_URL = resolveApiBaseUrl()`), mismo
    comportamiento que antes (env.ts lanzaba en evaluación): default si la env falta, error
    claro si existe pero es inválida. `new URL()` como validación (equivalente al
    `z.string().url()` anterior; sin restricción extra de protocolo para no ampliar alcance).
  - No se tocó `env.ts`: el fix debe desacoplar SOLO el cliente de búsqueda; la exigencia de
    Supabase del skeleton sigue siendo correcta para el resto de la app.
  - Sin tests nuevos: el contrato del cliente (URL default, timeout, errores) ya está cubierto
    por `buscar-page.test.tsx` (17 tests) y la regresión es estructural (build sin envs).
- **Tests añadidos**: ninguno (ver decisión); regresión cubierta por la verificación real.
- **Comandos ejecutados**:
  - Causa raíz: `env -u NEXT_PUBLIC_SUPABASE_URL -u NEXT_PUBLIC_SUPABASE_ANON_KEY
    node_modules/.bin/tsx -e "import('./src/lib/env.ts')…"` → **THROW** (env.ts:33).
  - Reproducción del fallo (código original, `git stash`): `env -u NEXT_PUBLIC_SUPABASE_URL
    -u NEXT_PUBLIC_SUPABASE_ANON_KEY pnpm build` → **FALLA** prerenderizando `/buscar`
    (`Error: Variables de entorno públicas inválidas o ausentes … src/lib/env.ts:33`),
    idéntico al CI.
  - Verificación clave (con el fix): mismo comando → **exit 0**, `/buscar` estática generada.
  - Gates: `pnpm format:check` ✅ · `pnpm lint` ✅ · `pnpm typecheck` ✅ · `pnpm test` ✅
    **20/20** (env 2 · home 1 · buscar 17 — sin regresiones).
  - Smoke E2E (puertos 3000/3100 ocupados por otros procesos → 3200 libre): `pnpm build` +
    `pnpm start -p 3200` + `WDIO_BASE_URL=http://localhost:3200 pnpm test:e2e:smoke` →
    **2 spec files / 5 tests passing** (home 1 + `/buscar` 4, stub HTTP real en
    `127.0.0.1:8000` vía `onPrepare` de `wdio.conf.ts`, parado limpio).
- **Resultados**: build de producción verde **sin ninguna env de Supabase**; quality gates
  verdes; E2E smoke verde; diff de 1 archivo de código.
- **Limitaciones**: la validación `new URL()` acepta cualquier esquema (paridad con el
  `z.string().url()` anterior); no se ejecutó `test:db` (requiere Supabase local y no aplica:
  cero cambios en BD/Supabase).
- **Riesgos**: bajo — cambio aditivo aislado en un módulo cliente; el default y el
  comportamiento del contrato no cambian; sin dependencias nuevas.
- **Trabajo pendiente**: orquestador → revisión independiente (otro agente) y merge a la rama
  de fase; CI quality del PR debe quedar verde con el job sin envs de Supabase.
- **Instrucciones para el revisor**: verificar (1) `grep -n "lib/env" src/lib/api/xtrace.ts`
  → sin coincidencias; (2) `env -u NEXT_PUBLIC_SUPABASE_URL -u NEXT_PUBLIC_SUPABASE_ANON_KEY
  pnpm build` en local (o CI) pasa; (3) `pnpm test` 20/20 sin cambios en tests; (4) el error
  claro solo se dispara si `NEXT_PUBLIC_XTRACE_API_URL` existe pero es inválida (p. ej.
  `NEXT_PUBLIC_XTRACE_API_URL=no-es-url pnpm build` → mensaje en el build).
