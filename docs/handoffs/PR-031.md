- **Decisiones tomadas**:
  - **Estructura HTML asumida** (documentada en `tests/fixtures/xvideos/README.md`
    y en el docstring del adapter): listado = `div.thumb a[href^="/video"]`
    (ID por regex `^/video(\d+)`, dedup) + `div.pagination a.next-page[href]`
    (cursor = path, `None` en la última página); página de vídeo = canonical
    `link[rel="canonical"]` (ID), título `h2.page-title`, datos del bloque JSON
    `flashvars` del reproductor (`duration` segundos, `timestamp` unix,
    `thumb_url`, `thumb_sprite`, `preview_video`) y tags `div.video-tags-list a`.
    *Por qué*: conocimiento público del layout de xvideos y convenciones de
    extractores públicos (youtube-dl `XvideosIE`); `flashvars` es el canal
    estable del reproductor. La captura real (PR-033) validará/ajustará; el
    fallo queda aislado en el adapter (SC-008) y los tests de regresión sobre
    los fixtures lo señalan.
  - **`limit` en `discover` sin pérdida de IDs**: si la página tiene más IDs que
    `limit`, `next_cursor` repite el cursor recibido (misma página); el llamador
    repite mientras reciba exactamente `limit` IDs y avanza al recibir menos.
  - **`get_video`**: 404 → `None` (vídeo retirado); página sin ninguna señal de
    vídeo (ni canonical, ni título, ni flashvars — p. ej. captcha/anti-bot o
    HTML cambiado) → `XvideosParseError` (el job queda `failed` con causa);
    otros errores HTTP se propagan (reintento transitorio). `check_availability`:
    404 → `removed`, página válida → `available`, resto → `unavailable`.
  - **`get_visual_assets` filtra por `manifest.assets_accessed`**: el
    `preview_url` se parsea y queda como metadata del `VideoSource` (lo exige
    el contrato) pero no se expone como asset mientras el manifest no declare
    `preview` (SEC-002); cuando la revisión legal (PR-033) lo apruebe, basta
    actualizar el manifest. Orden de jerarquía FR-005: storyboard → thumbnail.
  - **Manifest**: `source="xvideos"`, `access_method="html"`,
    `assets_accessed=["storyboard","thumbnail"]`, rate limit conservador
    (`min_interval_ms=2000`, `max_rps=0.5`), `review_date=None`.
  - El adapter no integra el rate limiter ni el registry: capas de PR-022/PR-028.

  Adapter listo técnicamente y bloqueado por diseño (manifest sin revisión

- **Limitaciones**:
  - La estructura HTML asumida es una hipótesis documentada hasta la captura
    real (PR-033): si difiere, se ajustan fixtures + selectores en PR-033.
  - El gate de habilitación del registry (SEC-002) no es testeable aquí:
    `registry.py` es de PR-028 (no mergeado); este PR fija el manifest
    deshabilitado por diseño y su test.
  - `check_availability` asume 404 como señal de vídeo retirado; si xvideos
    sirve una página "removed" con 200, PR-033 deberá añadir el marcador.
  - La regex de `flashvars` (`flashvars = {...};`) es no-greedy hasta el primer
    `};`: suficiente para el patrón real conocido; PR-033 la validará.
- **Riesgos**:
  - Cambios de HTML de xvideos → regresión detectada por los tests de fixtures
    (mensajes claros), fallo contenido en el adapter (SC-008).
  - Riesgo legal → mitigado por diseño: sin `robots_reviewed`/`terms_reviewed`
    el adapter no es habilitable (SEC-002); rate limit conservador en el
    manifest; el `preview` no se ofrece como asset hasta aprobación.
  - `selectolax` 0.4.11 (nueva dependencia): incluye `py.typed`/stubs (mypy
    estricto OK) y es la librería prevista en el plan (§Primary Dependencies).
