## Contrato de salida de `search` (contracts §1, JSON exacto por stdout)

```json
{
  "search_id": "uuid",
  "processing_ms": 1234,
  "results": [
    {
      "video_id": "uuid",
      "local_ref": "…",
      "match_score": 0.0,
      "matching_frames": 0,
      "match_timestamp_ms": 94000,
      "evidence": { "visual": 0.0, "phash": 0.0 }
    }
  ]
}
```

- `search_id`: uuid4 (verificado por test: versión 4).
- `processing_ms`: entero ≥ 0 (milisegundos reales de la invocación).
- `results`: ordenados por `match_score` descendente (PR-013); `local_ref`
  desde `public.videos` en backend postgres, `null` en in-memory (decisión de
  este PR, ver abajo); `match_timestamp_ms` puede ser `null` (FR-012);
  `evidence` siempre con las claves `visual` y `phash`.
- Índice vacío o sin coincidencias ≥ `min_score` → `"results": []`.
- Los vídeos excluidos nunca aparecen (FR-014): el ANN los filtra por defecto
  (PR-007) y el ranking re-filtra (PR-013).

## Contrato de salida de `exclude` (FR-014)

El JSON de este comando **no está definido en contracts §1**; este PR lo fija y
lo documenta aquí (pendiente de que el orquestador lo añada al contrato si
procede):

```json
{ "video_id": "<id>", "excluded": true, "changed": true }
```

- Postgres: `PgRepo.exclude` (PR-013) → `changed` = True si el estado cambió,
  False si ya estaba excluido o el vídeo no existe (idempotente; no borra
  registros, FR-014).
- In-memory: `InMemoryVectorStore.delete_video` (elimina frames del vídeo y lo
  marca excluido; PR-003) → `changed: true`. El índice in-memory es volátil
  por diseño (ADR-0006).

## Validaciones de entrada (spec §80 · ASSUMPTION-6 · ADR-0008 · security.py)

Orden de comprobaciones en `validate_query_image` (rechazo → `QueryMediaError`,
subclase de `ValueError` → exit 2 con JSON de error; la media rechazada **no se
modifica ni se borra**):

1. **Fichero regular existente** — `Path.is_file()`: inexistente o directorio →
   error.
2. **Tamaño ≤ 10 MB** — `MAX_QUERY_IMAGE_BYTES = 10 * 1024 * 1024` (límite
   inicial configurable de la spec §80): > 10 MB → error.
3. **Firma MIME por magic bytes** (nunca por extensión ni Content-Type,
   ADR-0008): JPEG `FF D8 FF`, PNG `89 50 4E 47 0D 0A 1A 0A`, WebP
   `RIFF....WEBP` (`ALLOWED_QUERY_IMAGE_MIME = {image/jpeg, image/png,
   image/webp}`). Un fichero renombrado o con extensión falsa se rechaza.
4. **Decodificación forzada** — `open_query_image` (PIL) hace `load()`: firma
   válida pero contenido ilegible (truncado/corrupto) → `QueryMediaError`
   (exit 2) antes de entrar en el pipeline. Otros `OSError` de I/O real se
   propagan como fallo de ejecución (exit 1).

## Borrado inmediato de la media de consulta (FR-018 · ADR-0006 · FR-009/SC-006)

- `QueryMediaContext.from_file(image, work_root)` (security.py): copia la media
  a un **temporal seguro** con `tempfile.mkstemp` (nombre impredecible, prefijo
  `xtrace-query-`, permisos **0600**, dentro del work_root del llamador) y su
  `__exit__`/`cleanup()` borra **siempre** (try/finally) la copia y el fichero
  original, tanto si la búsqueda termina con éxito como si el procesamiento
  falla (FR-009 · SC-006: sin temporales residuales). Un fallo de borrado se
  registra como warning y no enmascara el resultado del bloque.
- El procesado trabaja **solo sobre la copia**, nunca vuelve a abrir la ruta
  original tras la validación (defensa ante modificación entre validación y
  uso, ADR-0006).
- La media **rechazada por validación no se borra** (el contexto solo se crea
  tras `validate_query_image`): verificado por tests (MIME inválido, oversize,
  `--top-k 0`).
- El contrato §5 sigue intacto: ningún contrato expone/almacena la media de
  consulta.
