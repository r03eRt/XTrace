- **Resumen**: Nuevo runner `BenchmarkRunner` (FR-016) que ejecuta los casos
  del dataset de benchmark (PR-015: `BenchmarkCase` + `load_manifest`) contra
  el índice usando la cadena de búsqueda real (PR-012/013/014), nunca una
  copia: `ImageSearch.search_image` (normalizar → pHash → embed → ANN →
  agrupar) + `rank_candidates` (match_score, evidencia pHash con el mismo
  criterio de resolución de frames que la CLI search) y produce el informe
  del contrato CLI §1. Nuevo comando `benchmark` en la CLI (FR-017): JSON
  del contrato por stdout con exit 0, JSON de error con exit 2 para errores

    del contrato — cases, top1, top5, top10, false_positive_rate_negatives,
    latency_ms {p50, p95}, frames_per_video_avg, index_size_bytes,
    embedding_throughput_fps. top1/top5/top10 y FPR con precisión de 4

    los 5 / 10 primeros resultados rankeados; el vídeo esperado se

    el umbral real lo fija el operador en la evaluación SC-002.

  - **SC-007 (reproducibilidad)**: el informe no contiene timestamps ni
    aleatoriedad; top1/5/10, FPR, frames/vídeo y tamaño del índice son

    que acumula imágenes y tiempo real de `embed_images`;

- **Limitaciones**:
  - Las puertas SC-001/SC-002 sobre el dataset REAL (210 casos) requieren
    índice real (SigLIP + DB); el fixture valida la mecánica del runner y
    las puertas con provider fake determinista.

    representativo del provider real (SigLIP): es una métrica de la
    ejecución, no de calidad.
  - `index_size_bytes` siempre 0: ningún store lo expone en stats (ver
    Decisiones).

    default sin leer la semántica puede malinterpretar SC-002 (documentado
