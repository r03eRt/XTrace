- **Resumen**: Se implementa el **ranking configurable** del spike
  (FR-012/013/014 · ADR-0005 · contracts §4): `search/ranking.py` consume el
  `ImageSearchResult` de PR-012 (query_phash + VideoCandidate) y combina, con

## Pesos por defecto (FR-013 · decisión de este PR)

- `DEFAULT_WEIGHTS = RankingWeights(visual=0.5, frames=0.3, phash=0.2)`.
  La similitud visual (señal principal del ANN, ADR-0005) domina; nº de
  frames y pHash son evidencia de apoyo. **Configurables**: cualquier
  `RankingWeights(v, f, p)` con pesos >= 0 y suma > 0; se **normalizan
  internamente** a suma 1 (pesos relativos: (2,2,2) ≡ (1,1,1)), de modo que
  `match_score` queda siempre en [0,1]. Un peso a 0 desactiva su señal.
  Validación en `RankingWeights.__post_init__` (ValueError si algún peso es
  negativo o la suma es <= 0). El benchmark PR-016 calibrará estos valores
  contra SC-001/SC-002 (punto de partida documentado en el módulo).

## Fórmula del score (FR-012/013)

    s_visual = clamp01(1 − best_distance)                # coseno, contracts §2/§5
    s_frames = matching_frames / max(matching_frames)    # máx. entre candidatos NO excluidos
    s_phash  = clamp01(1 − Hamming(query_phash, phash_del_mejor_frame) / 64)   # 0 si falta el pHash

    match_score = (w_v·s_visual + w_f·s_frames + w_p·s_phash) / (w_v + w_f + w_p)   # ∈ [0,1]

- `match_timestamp_ms = best_timestamp_ms` del candidato (None si el mejor
  frame no tiene timestamp; FR-012).
- `min_score` (default `DEFAULT_MIN_SCORE = 0.0` = sin rechazo): descarta
  resultados con `match_score < min_score` (validado en [0,1]).
- Orden: `match_score` descendente; desempates por `best_distance` ascendente
  y `video_id` (orden estable y determinista).
- Ejemplo verificado por test (pesos por defecto): visual 0.8, frames 1.0,
  phash 0.75 → score = (0.5·0.8 + 0.3·1.0 + 0.2·0.75)/1.0 = **0.85**.

## Decisión: acceso al pHash de los frames (FR-013 · FIX-phash)

- `rank_candidates` es **función pura**: la evidencia pHash se recibe como
  parámetro `frame_phashes: Mapping[str, int]` (frame_id → pHash SIN signo
  de 64 bits, salida de `compute_phash`). Un frame ausente del mapeo
  contribuye **0** a la evidencia (neutral, sin penalizar el resto).
- En producción el llamador lo obtiene de la DB con el nuevo método
  **`PgRepo.get_frame_phashes(frame_ids)`** (repo.py): SELECT sobre
  `frames.phash` (bigint con signo) + decodificación con `phash_from_db`
  (vectorstore/pgvector.py). El import de `phash_from_db` es **a nivel de
  función** para evitar el ciclo de módulos (pgvector.py importa repo.py).
  Devuelve solo los frame_ids existentes; validación temprana de UUID;
  lista vacía → {}.
- Alternativas consideradas y descartadas: duplicar el codec bigint→pHash en
  repo.py (riesgo de divergencia) y exponer el valor crudo con signo (API
  con trampa, rompe el contrato de `hamming_distance`).
- El cableado completo (ImageSearch → get_frame_phashes → rank_candidates)
  es del CLI search de PR-014.

## Exclusión (FR-014)

- `PgRepo.exclude(video_id, *, excluded=True) -> bool`: UPDATE
  `videos.excluded` **solo cuando el estado cambia**
  (`where id = %s and excluded is distinct from %s`) — devuelve True si el
  estado cambió, False si el vídeo no existe o ya tenía el estado pedido.
  No borra registros (FR-014: sin borrado necesariamente irreversible).
  Detalle encontrado en smoke contra la DB: Postgres reporta rowcount=1
  aunque el valor no cambie; el `is distinct from` corrige la semántica
  documentada.
- `rank_candidates(..., excluded_videos=...)`: filtra los candidatos cuyo
  video_id está excluido **antes** de puntuar (y el máximo de frames para la
  normalización se calcula sobre los no excluidos). Mecanismo
  complementario al filtro por defecto de `ann_search(exclude_videos=True)`
  (PR-007), que ya no devuelve frames de vídeos excluidos en producción.
