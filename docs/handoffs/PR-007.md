- **Resumen**: Implementación real del contrato `VectorStore` (contracts §2)
  sobre **pgvector/HNSW (coseno)** en Supabase: `PgVectorStore`
  (`vectorstore/pgvector.py`) usando la tabla `frames` de la migración PR-006
  (embedding `vector(768)`, índice `idx_frames_embedding_hnsw` con
  `vector_cosine_ops`). Acompañado de `repo.py` (capa de datos: DSN
  configurable, conexiones async y garantía de existencia de `videos` para la
  FK) y de la suite de integración `tests/integration/test_pgvector_store.py`
  (9 tests contra Supabase local, con paridad verificada contra
  `InMemoryVectorStore` y skip automático sin DB). Driver: **psycopg 3.3.4
  async** (`AsyncConnection`).

- **Requisitos implementados**:
  - **FR-006**: `PgVectorStore` persiste frame_id/video_id/timestamp_ms/embedding
    en `frames` y consulta por ANN: `embedding <=> $1` (distancia coseno,
    menor = más similar), ORDER BY ASC, LIMIT k, vía el índice HNSW
    (verificado con EXPLAIN: `Index Scan using idx_frames_embedding_hnsw`).
  - **FR-008/SC-005**: upsert **idempotente** con `ON CONFLICT (video_id,
    frame_seq)`: `frame_seq = timestamp_ms` cuando hay timestamp, o un ordinal
    estable del lote (offset 1e9) si no; el re-upsert reemplaza (DO UPDATE), no
    duplica. Verificado con re-upsert idéntico y con clave igual + frame_id nuevo.
  - **FR-014**: `delete_video` elimina los frames y marca `videos.excluded =
    true` (paridad con InMemoryVectorStore); `ann_search(exclude_videos=True)`
    (default) filtra vídeos `excluded` vía JOIN a `videos`; `False` los incluye.
  - **FR-007 (base)**: `repo.py` (`PgRepo.ensure_video`) garantiza la fila
    `videos(id)` para satisfacer la FK de `frames` (ON CONFLICT DO NOTHING:
    no pisa el `local_ref`/estado reales que fijará el pipeline PR-010).
  - **SC-003**: la consulta ANN usa HNSW (plan verificado); la latencia p95 se
    mide formalmente en PR-016.
  - **ADR-0004/0007**: implementación real tras la abstracción `VectorStore`
    (Protocol, contracts §2); invariante coseno contracts §5.

- **Decisiones tomadas**:
  - **Driver: psycopg async** (`AsyncConnection`). El contrato es 100 % async;
    con psycopg 3.3.4 no hace falta envolver sync en threads. `autocommit=True`
    por conexión: el spike es CLI local y la validación de contrato (uuid,
    dimensión) ocurre en Python **antes** de ejecutar SQL, así que no hay
    estados parciales por errores de contrato. Sin pool (escala CLI).
  - **DSN**: constructor (`PgVectorStore(dsn=…)`) y entorno
    (`SUPABASE_DB_URL`, nombre documentado en quickstart.md); default
    `postgresql://postgres:postgres@127.0.0.1:55322/postgres` (Supabase local,
    config.toml; postgres superuser → bypass RLS, equivalente a service_role).
  - **Adaptación de `vector` sin dependencia nueva**: el paquete Python
    `pgvector` no está en pyproject.toml (no editable en esta tarea), así que
    el embedding viaja como **literal de texto** `'[x,y,…]'` casteado con
    `::vector` (formato de entrada nativo de pgvector). Dimensión validada en
    Python con el mismo ValueError que el doble in-memory (paridad).
  - **Clave de idempotencia**: `ON CONFLICT (video_id, frame_seq)` (uno de los
    dos uniques de la migración PR-006, FR-008 "vídeo + posición/timestamp"):
    - frames con timestamp → `frame_seq = timestamp_ms` (estable aunque cambie
      el orden del lote; < 1e9 ms ≈ 11,6 días para cualquier vídeo real);
    - frames sin timestamp → `frame_seq = 1e9 + ordinal del lote` por vídeo
      (estable si el lote es estable; no colisiona con la familia anterior);
    - el DO UPDATE refresca `id = excluded.id` (el frame_id del contrato es la
      PK de `frames`), `timestamp_ms`, `phash` y `embedding`.
  - **`phash` centinela = 0**: `frames.phash` es NOT NULL pero el contrato
    `FrameRecord` (contracts §2) **no** transporta phash (base.py: fuera de la
    responsabilidad del VectorStore). Decisión abierta para el orquestador:
    ampliar el contrato o persistir phash vía repo.py en PR-010/013.
  - **Auto-creación de vídeos en `upsert_frames`**: necesaria para paridad de
    contrato (InMemoryVectorStore acepta cualquier video_id; la FK de `frames`
    exige la fila). `ensure_video` usa `local_ref = video_id` como respaldo
    cuando no hay ref real; ON CONFLICT DO NOTHING preserva la fila real que
    cree el pipeline (PR-010).
  - **`stats`** = `count(distinct video_id)`, `count(*)`, `count(*)` sobre
    `frames`: mismo criterio que InMemoryVectorStore (vídeos con ≥ 1 frame;
    tras `delete_video` el vídeo excluido sin frames deja de contarse).
  - **`ann_search` con k ≤ 0 → []** (sin error; paridad con PR-003). El filtro
    de exclusión se pliega a constante en plan time (`%s = false or not
    v.excluded`) y no rompe el escaneo HNSW (EXPLAIN verificado).
  - Tests async sin pytest-asyncio (no está en deps): `asyncio.run` por test,
    igual que PR-003. Skip de módulo vía `pytestmark = skipif(no DB)` con
    conexión sincrónica `connect_timeout=2` en recolección.

- **Limitaciones**:
  - `phash` se persiste como **0** (centinela): el contrato FrameRecord no lo
    transporta. Si PR-010/013 necesita pHash real en `frames`, el orquestador
    debe decidir cómo (extender `FrameRecord` o método nuevo en `repo.py`).
  - La idempotencia de frames **sin timestamp** depende del orden estable del
    lote (ordinal): reordenar un lote puede duplicar (la clave estable es
    "vídeo + posición"). Los frames con timestamp son robustos a reordenación.
  - `frame_seq = timestamp_ms` asume timestamps < 1e9 ms; para vídeos reales
    (duración ≪ 11,6 días) es seguro. No hay constraint DB que lo fuerce.
  - Empates de distancia entre frames distintos: el orden entre ellos no está
    definido (HNSW/ORDER BY); los tests evitan empates a propósito.
  - Una conexión por operación (sin pool): suficiente para la CLI del spike;
    revisar si el servicio creciera.
  - RLS deny-by-default: se accede como postgres superuser local (bypass). En
    cloud habrá que usar el DSN con service_role vía `SUPABASE_DB_URL`.

- **Riesgos**:
  - Parámetros HNSW por defecto de pgvector (m, ef_construction, ef_search):
    tuning medido en PR-016/017 (SC-001/SC-003).
  - La exclusión vía JOIN + filtro se validó con EXPLAIN; si el dataset crece
    mucho, el filtro post-ANN puede requerir `excluded` en el índice o
    revalidar el plan (fuera del alcance del spike).
  - El contrato transporta frame_id como str pero la DB exige uuid: frame_id
    inválido → ValueError explícito (el doble in-memory no valida; divergencia
    documentada y deliberada).
