# Handoff — PR-059

- **Proveedor y modelo usados**: `provider: deepseek-official · model: deepseek-v4-flash`
- **Resumen**: Fix del smoke E2E de `/buscar` (spec 003 · **SC-005**): se elimina la
  interceptación BiDi (frágil: carreras «No blocked request found for network id …» en el
  HEAD fusionado) y el E2E habla por **HTTP real** con un **stub Node nativo sin
  dependencias** (`tests/e2e/stub-api.mjs`) que escucha en `127.0.0.1:8000` (default de
  `NEXT_PUBLIC_XTRACE_API_URL`) y arranca desde `wdio.conf.ts` antes de la suite. Smoke
  **5/5 verde en 3 ejecuciones consecutivas** (determinista).
- **Requisitos implementados**:
  - **SC-005**: `pnpm test:e2e:smoke` verde sin API real en CI (stub HTTP real; sin
    interceptación de red).
  - **FR-009/FR-010/UX-003** (E2E): resultados con título, fuente, score, timestamp y
    enlace «Ver original» con `href` del fixture; resultado local → `local_ref` sin
    enlace y timestamp «—».
  - **UX-002** (E2E): feedback de carga visible durante el retardo del stub y botón
    deshabilitado.
  - **FR-011/UX-001** (E2E): fichero no imagen → error de validación en español **sin**
    llamar a la API (asertado con el contador `GET /__count` del stub, delta 0); `bad.png`
    → 415 del stub (contracts §5) → mensaje en español en la UI.
- **Archivos modificados** (solo `allowed_paths`):
  - `tests/e2e/stub-api.mjs` (nuevo): `POST /search` (multipart; nombre que empieza por
    `bad` → 415 §5; resto → retardo y fixture `search-response.json`), `GET /health`
    (contracts §2), `GET /__count` (contador), CORS `*` + preflight OPTIONS, graceful
    SIGTERM/SIGINT.
  - `wdio.conf.ts` (solo el bloque del stub): arranque/parada del stub con los hooks
    estándar `onPrepare`/`onComplete` (ver decisión D1). Nada más se tocó.
  - `tests/e2e/specs/search.smoke.e2e.ts` (reescrito): sin BiDi; 4 tests contra el stub
    real con aserciones de contador.
  - `tests/e2e/fixtures/bad.png` (nuevo: PNG sintético 1×1, copia de `query.png`).
  - `docs/handoffs/PR-059.md` (este handoff).
- **Decisiones tomadas**:
  - **D1 — `webServer` no existe en WebdriverIO v9**: la opción `webServer` del config se
    eliminó en v9 (v8); verificada su ausencia en `@wdio/types`/`@wdio/local-runner`
    9.30.1 instalados y en la doc oficial (404). Añadirla rompería `tsc` y sería ignorada
    en runtime. Sustitución equivalente y estándar v9: `onPrepare` arranca
    `node tests/e2e/stub-api.mjs` (espera `GET /health` con timeout 30 s) y `onComplete`
    envía SIGTERM (el stub cierra graceful). Mismo resultado que el `webServer` previsto:
    el stub lo arranca `wdio.conf.ts` antes de la suite, también en CI.
  - **D2 — retardo de `/search` en 1500 ms** (env `STUB_SEARCH_DELAY_MS`, default 1500):
    el enunciado sugería ~300 ms, pero con 300 el estado de carga es apenas observable y
    el test UX-002 sería frágil en CI (objetivo del PR: determinismo; el retardo solo
    añade 1,5 s a la suite).
  - **D3 — `error_type` del 415 = `media_type_not_supported`** (contracts §5), no
    `media_invalid_type` como decía el enunciado: el contrato y la API real
    (`services/api/xtrace_api/media.py`) usan `media_type_not_supported`; el stub replica
    el mensaje real («la imagen de consulta debe ser JPEG, PNG o WebP (firma por
    cabecera)»).
  - **D4 — contador `GET /__count`** en el stub: aserciones «sin llamar a la API» (delta
    0) y «la petición llegó al stub» (delta 1 en feliz y 415), sin fixtures adicionales.
  - **D5 — CORS**: `Access-Control-Allow-Origin: *` + OPTIONS 204 (fetch cross-origin
    localhost:3000 → 127.0.0.1:8000).
  - **D6 — `bad.png`** es un PNG real 1×1 (pasa la validación de cliente) cuyo **nombre**
    dispara el 415 en el stub — simula el edge case «fichero renombrado/extensión falsa»
    sin contenido real.
  - **Nota build (preexistente, fuera de alcance)**: `pnpm build` exige
    `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` (`src/lib/env.ts`,
    `src/**` prohibido para esta tarea). En CI las inyecta el repo (variables de Actions);
    localmente se usaron valores dummy de `.env.example` manteniendo
    `NEXT_PUBLIC_XTRACE_API_URL` en su **default** `http://127.0.0.1:8000` (verificado en
    el bundle: el E2E habla con el stub).
- **Comandos ejecutados y resultados**:
  - `pnpm build` → OK (env dummy Supabase; API URL default).
  - `pnpm test:e2e:smoke` → **5/5 verde ×3** (home 1 + buscar 4; app en `:3100` con
    `WDIO_BASE_URL` porque un `next start` huérfano del worktree PR-058 ocupa `:3000` —
    no se tocó; `WDIO_BASE_URL` es el knob documentado en `.env.example`).
  - `pnpm format:check` → OK · `pnpm lint` → OK · `pnpm typecheck` → OK ·
    `pnpm test` → 20/20 OK · `tsc -p tests/e2e/tsconfig.json` → OK (wdio.conf.ts + specs).
  - Stub verificado con curl: `/health`, `/__count`, `POST /search` (fixture y 415),
    preflight OPTIONS, 404, SIGTERM graceful.
- **Limitaciones/riesgos**:
  - El stub solo cubre lo que el E2E necesita (`/search`, `/health`, `/__count`); no
    implementa `/stats` ni `/videos/{id}` (no se usan en la smoke).
  - Si algo ya escucha en `127.0.0.1:8000` (p. ej. la API real del operador), `onPrepare`
    falla con mensaje claro (por diseño: respuestas no deterministas).
  - Sin cambios en `e2e.yml` ni `package.json` (allowed_paths): en CI el stub lo arranca
    wdio automáticamente.
- **Trabajo pendiente**: ninguno en esta tarea. SC-002/SC-004 siguen siendo la puerta
  manual del operador ya documentada en PR-058.
- **Instrucciones para el revisor**: verificar que `wdio.conf.ts` no cambió nada más que
  el bloque del stub (diff); ejecutar `pnpm test:e2e:smoke` con la app en marcha y sin
  nada en `:8000`; confirmar 5/5.
