- **Resumen**: La CLI del spike (PR-001, solo `--help`/`--version`) gana los
  subcomandos **`index`** y **`stats`** (contracts §1, FR-017). `index`
  cablea el pipeline de PR-010 (`IndexingPipeline` + `IndexingConfig` +
  `scan_dataset`) con backend y proveedor de embeddings **configurables por
  entorno/flag**, y emite por stdout el JSON exacto del contrato
  (`videos_indexed`/`videos_failed`/`frames`/`vectors`). `stats`
  reporta las métricas del índice (`videos`/`frames`/`vectors` +
  etiqueta de backend + model_id del proveedor) en JSON estable. La salida es
  SIEMPRE JSON por stdout; los logs de progreso van a stderr. Códigos de
  salida: 0 éxito, 2 error de uso/validación, 1 fallo en ejecución.
- **Requisitos implementados**:
  - **FR-017 / contracts §1 (index)**: `xtrace-spike index --dataset <path>
    [--frames-per-video 30] [--dedupe-threshold 10] [--batch-size 64]`
    (defaults del contrato; --provider opcional). Reutiliza el pipeline
    PR-010 con las tres interfaces inyectadas (ADR-0007): VectorStore,
    EmbeddingProvider y VideoStateStore. Salida:
    `{"videos_indexed": n, "videos_failed": m, "frames": f, "vectors": v}`
    con el orden de claves del contrato (JSON estable).
  - **FR-017 / contracts §1 (stats)**: `xtrace-spike stats` -> métricas del
    índice vía `VectorStore.stats()` (contracts §2): `videos` (vídeos con
    ≥ 1 frame indexado, mismo criterio que Pg), `frames`, `vectors`; la
    CLI añade `backend` ("in-memory" | "postgres") y `embedding_provider`
    (model_id) para observabilidad. Orden de claves estable.
  - **Salida JSON por stdout, logs a stderr (contracts §1)**: progreso con
    `typer.echo(..., err=True)`; los warnings del pipeline (p. ej. vídeo
    fallido) ya van a stderr por logging. Verificado por test: stdout parsea
    como JSON puro.
  - **Resiliencia (FR-001 US1 esc. 3)**: un vídeo corrupto se cuenta en
    `videos_failed` y el resto del dataset continúa (verificado por test y
    por ejecución real).

- **Decisiones tomadas**:
  - **Backend por env (documentada en cli.py y este handoff)**: si
    `SUPABASE_DB_URL` está definida -> `PgVectorStore` +
    `PgVideoStateStore` (producción, PR-007/PR-010); si no ->
    `InMemoryVectorStore` + `InMemoryVideoStateStore` (PR-003,
    determinista, sin DB). La CLI usa Pg SOLO con la env definida (aunque
    `repo.resolve_dsn()` tenga default local) para que los runs sin
    configuración sean deterministas e in-memory.
  - **Índice in-memory por proceso (lru_cache)**: `build_backend()` está
    cacheada por proceso para que `index` -> `stats` compartan el mismo
    índice en una sesión (tests y uso interactivo). Entre procesos reales el
    índice in-memory no persiste: `stats` sin env reporta ceros (índice
    volátil por diseño, ADR-0006: no se almacenan originales). Documentado
    como limitación.
  - **Embeddings configurables**: `FakeEmbeddingProvider` (PR-002) por
    defecto; `SiglipLocalProvider` (PR-005) con `--provider siglip` o
    `XTRACE_EMBEDDING_PROVIDER=siglip`. El flag explícito gana sobre la
    env; valor desconocido -> error JSON exit 2. La carga de Torch es lazy
    (PR-005): `stats --provider siglip` funciona sin el extra instalado.
  - **Comandos sync + `asyncio.run`**: typer 0.27.1 (click vendido en el
    paquete) NO soporta funciones async (no hay asyncio/iscoroutine en su
    runtime: el coroutine se devolvía sin await). Los comandos son sync y
    ejecutan el pipeline async con `asyncio.run(...)` (un event loop por
    invocación; los stores son agnósticos al loop). Hallazgo documentado.
  - **JSON de error estable**: `{"error": <mensaje>, "error_type": <Tipo>}`
    por stdout. Códigos de salida: 0 éxito; 2 uso/validación (`DatasetError`
    de scan_dataset, `ValueError` de IndexingConfig y proveedor); 1
    cualquier otra excepción en ejecución (p. ej. DB inaccesible).
  - **stats amplía el mínimo del contrato**: `videos`/`frames`/`vectors`
    (contracts) + `backend` + `embedding_provider` (observabilidad); sin
    romper el contrato (claves añadidas, orden estable).

- **Limitaciones**:
  - **stats sin DB en procesos distintos reporta ceros**: el backend
    in-memory es por proceso (lru_cache); entre invocaciones reales de la
    CLI no hay persistencia (ADR-0006). Con `SUPABASE_DB_URL` definida el
    índice es real y `stats` reporta los totales de la DB.
  - **Errores de uso de Click/Typer fuera de nuestro control**: opción
    desconocida o valor no-entero en opciones int -> Click imprime el error
    en stderr con exit 2 y stdout vacío (no JSON). Los errores de NEGOCIO
    (dataset, config, proveedor) sí emiten JSON por stdout. Aceptado: el
    contrato exige JSON estable para la operación correcta y sus errores
    controlados.
  - No se añadió test de integración con PgVectorStore vía CLI (con
    SUPABASE_DB_URL): el camino Pg reutiliza PgVectorStore/PgVideoStateStore
    ya cubiertos por PR-007/PR-010, y el alcance de la tarea exige tests
    deterministas sin DB.
  - El flag `--provider siglip` en `index` requiere el extra `siglip`
    (torch/open_clip) en tiempo de ejecución del embedding (lazy, PR-005);
    sin el extra falla el vídeo o el dataset (error JSON exit 1) — esperado.
- **Riesgos**:
  - `asyncio.run` por invocación: un event loop nuevo por comando; los
    stores actuales son agnósticos al loop, pero un store futuro ligado a
    loop (p. ej. conexiones reutilizadas) rompería — revisar en PRs
    posteriores (PR-014).
  - La etiqueta `embedding_provider` expone el model_id (estable, sin
    secretos); si el contrato CLI llegara a exigir claves exactas en stats,
    ajustar (el contrato solo fija index; stats es observabilidad).
  - Los conteos de dedupe sobre testsrc2 no se asertan (dependen de
    imagehash): los tests asertan invariantes (0 < frames ≤ N×vídeos,
    igualdad entre index y stats) — robustos.
