- **Decisiones tomadas**:
  - Validación reutilizando solo funciones del spike (`validate_query_image`, `detect_query_image_mime`, `open_query_image`); el 413 se decide por streaming en la subida (límite = `MAX_QUERY_IMAGE_BYTES`, misma constante).
  - El handler es **sync** (threadpool de FastAPI) con `asyncio.run` para la cadena async (mismo patrón que la CLI, plan §Scale/Scope).
  - Doble borrado: `QueryMediaContext` (spike) alrededor del procesado + `finally` del handler sobre el temporal de subida (plan §Security strategy). La media rechazada también se borra (en la API el fichero es nuestro).
  - **Analítica solo con backend postgres** (FR-012): en modo in-memory (tests/dev sin BD) no hay tabla `searches` que registrar; además evita colgarse intentando conectar a la BD por defecto cuando no hay stack (ver Limitaciones). `record_search` es best-effort: si la BD cae tras la búsqueda, se loguea warning sin enmascarar el resultado (mismo criterio que el fallo de borrado).
  - `top_k` acotado a [1, 1000] en la API (defensa, contrato no lo acota; el default es 10) — desviación documentada: `top_k > 1000` que la CLI aceptaría responde 400 `invalid_request`.
  - `error_type` nuevo `invalid_request` para campos de formulario inválidos (la tabla del contracts §5 no lo lista; es 400 genérico "solicitud inválida").
  - `RequestValidationError` (body no multipart, 422 de FastAPI) → 400 `missing_file_part` (contrato no contempla 422).
  - Imports de `xtrace_spike` con `# type: ignore[import-untyped]` (política del crawler, PR-037).
