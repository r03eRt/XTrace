## Resumen

Implementado el adapter real **`redgifs`** (`services/crawler/xtrace_crawler/
adapters/redgifs.py`): primer adapter del SDK con `access_method="api"`. Habla
solo con `api.redgifs.com` (token temporal `GET /v2/auth/temporary`, listado de
nicho paginado por `page`, objeto gif `GET /v2/gifs/<id>`), **nunca** con
`www.redgifs.com`. Assets v1 = thumbnail + poster (ambos `kind="thumbnail"`, sin
timestamp); nunca los mp4 (`sd`/`hd`/`silent`). `discover()` exige `section` con
prefijo `/niches/` (fail-fast, D2). `page_url` fijo, nunca fetcheado (D5).
Fixtures sintéticos JSON anonimizados (dominio `.invalid`) + 44 tests unitarios
sin red (`httpx.MockTransport`). El adapter **no está registrado** en el CLI
todavía (eso es PR-067): este PR es autocontenido y no toca el core.

## Amendment de infraestructura (fuera de `allowed_paths` originales, documentado)

`RedgifsAdapter` es el primer adapter que necesita enviar un header
`Authorization: Bearer <token>` por request — ningún adapter anterior (HTML,
sin auth) lo necesitaba. `SafeHTTPClient.get()` no aceptaba headers
adicionales. Se extendió de forma **puramente aditiva** (`services/crawler/
xtrace_crawler/crawling/http.py`): nuevo parámetro `headers: dict[str, str] |
None = None`, `None` (default) preserva el comportamiento exacto de siempre —
ningún adapter existente cambia de comportamiento. Se añadió un test dedicado
en `tests/unit/test_http.py`
(`test_get_headers_opcionales_se_anaden_sin_sustituir_los_por_defecto`).

Esto es un cambio de infraestructura HTTP genérica (no de contrato de negocio:
no toca `adapters/base.py`, `models.py`, `registry.py`, `pipeline.py`, `jobs/*`),
pero sí toca un fichero del core en sentido estricto (`crawling/http.py`). Se
documenta aquí explícitamente para que el orquestador/revisor lo valide como
excepción mínima y trazable, no como un cambio silencioso (constitución §1).
Si el revisor lo considera fuera de alcance de PR-066, la alternativa sería una
enmienda formal previa a la spec 002 — quedo a la espera de esa decisión antes
de PR-067.

## Decisiones

- Cache en memoria (`self._gif_cache`) de objetos gif ya vistos en el listado
  más reciente de esta instancia: `get_video()` evita un segundo GET cuando el
  ítem viene de un `discover()` reciente (ADR-0016 §5, optimización — no forma
  parte del contrato).
- `urls.poster` se guarda en `VideoSource.storyboard_urls` (contenedor
  genérico reutilizado; redgifs no tiene storyboard/sprite) — documentado en el
  docstring del módulo y de `parse_gif_object` para que no se confunda con un
  storyboard real.
- Renovación del token: una sola renovación por petición ante `401`; un fallo
  persistente se propaga como `httpx.HTTPStatusError` normal (contenido en la
  fuente, sin reintento infinito — el worker de jobs aplica su propio backoff
  por encima, paridad con el resto de fuentes).

## Limitaciones

- La estructura de la API usada es la **observada en prospección
  (2026-08-19)**, no validada end-to-end contra redgifs real: se re-valida en
  PR-069 con capturas reales del operador (`--max-videos 50` sobre
  `/niches/homemade` y `/niches/real-cellphone-clips`).
- El adapter aún no está registrado en `cli._default_registry()` ni tiene fila
  de seed (PR-067): no es invocable desde el CLI todavía.
- La extensión de `SafeHTTPClient.get()` (headers opcionales) es la primera
  vez que se toca un fichero fuera de `adapters/` en esta feature — ver
  "Amendment de infraestructura" arriba; el revisor debe confirmarla o pedir
  la vía de enmienda formal antes de seguir con PR-067.

## Riesgos

- El comportamiento real de renovación de token (¿la API devuelve 401 o algo
  distinto ante expiración?) es una asunción de la prospección; PR-069 lo
