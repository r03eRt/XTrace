- **Resumen**: Pipeline de indexación end-to-end (`indexing/pipeline.py`):
  por cada vídeo del dataset orquesta
  `extract_frames (PR-008) → dedupe_frames (PR-009) → embed_images en batches
  (FR-005) → VectorStore.upsert_frames (FR-006)`, con gestión de estado del
  vídeo (FR-007), ids estables por vídeo/frame (FR-008) y cleanup garantizado
  en try/finally (FR-009/SC-006/ADR-0006). Depende **solo** de interfaces
  (ADR-0007): `VectorStore`, `EmbeddingProvider` y `VideoStateStore` se
  inyectan por constructor; en tests se usan `InMemoryVectorStore` +
  `FakeEmbeddingProvider` + `InMemoryVideoStateStore` (deterministas, sin DB
  ni Torch) y en producción `PgVectorStore` + `SiglipLocalProvider` +
  `PgVideoStateStore`. El estado real (PostgreSQL, migración PR-006) se
  implementa en `indexing/state.py` reutilizando `PgRepo` (repo.py, PR-007)
  **sin modificar repo.py** (fuera de allowed_paths) y se valida con un test
  de integración opcional contra Supabase local.
- **Requisitos implementados**:
  - **FR-005**: `_embed_frames` agrupa los frames deduplicados en lotes de
    `batch_size` (configurable, default 64), abre/cierra las imágenes por
    lote y valida el contrato del proveedor (shape (N, D) con D =
    `provider.dimension`); embeddings convertidos a float nativo.
  - **FR-006**: `VectorStore.upsert_frames` con `FrameRecord` (contrato
    contracts §2): `frame_id`, `video_id`, `timestamp_ms`, embedding.
  - **FR-007**: `VideoStateStore` (Protocol) + `InMemoryVideoStateStore` +
    `PgVideoStateStore`; transiciones `discovered → indexing → indexed |
    failed` (dos fases en `index_dataset`: discover de todos, luego
    indexación por vídeo). `mark_indexed` registra `frame_count` y
    `duration_ms`; `mark_failed` registra el error.
  - **FR-008/SC-005**: ids deterministas (uuid5): `video_id_for(local_ref)`
    y `frame_id_for(video_id, frame_seq)` con `frame_seq` = timestamp_ms o
    ordinal desplazado 1e9 (paridad exacta con la clave de conflicto de
    PgVectorStore, PR-007). Reindexar re-upserta las mismas claves: el upsert
    es idempotente (InMemory por `frame_id`; Pg por
    UNIQUE(video_id, frame_seq)). Verificado por test: 2 ejecuciones → mismos
    frames/vectores/ids.
  - **FR-009/SC-006**: cada vídeo se procesa dentro del context manager
    `extract_frames` (PR-008 borra su dir temporal en finally) y
    `index_dataset` crea un dir temporal de ejecución (`xtrace-index-*`) que
    se elimina en finally pase lo que pase. Un vídeo que falla (corrupto,
    error de embedding, …) se marca `failed` y el resto del dataset continúa
    (FR-001 US1 esc. 3).
  - Trazabilidad: tests marcan FR/SC (constitución §3); edge cases de spec
    cubiertos (dataset vacío, vídeo corrupto, fallo a mitad de indexación).

- **Decisiones tomadas**:
  - **Ids estables con uuid5**: el contrato `FrameRecord` usa `frame_id`
    string (UUID para Pg); un uuid5(video_id, frame_seq) es determinista y
    compatible con ambos stores. `video_id` = uuid5(local_ref): clave estable
    por vídeo (FR-008) sin estado previo compartido.
  - **Paridad de `frame_seq` con PgVectorStore (PR-007)**: timestamp_ms o
    `1e9 + ordinal` para frames sin timestamp; así la idempotencia del
    pipeline coincide con la clave de conflicto ON CONFLICT (video_id,
    frame_seq) de la DB. La constante `_NULL_TS_SEQ_OFFSET` se duplica con
    docstring de paridad para no acoplar el dominio a la impl Pg (ADR-0007).
  - **Estado como tercera abstracción inyectable**: FR-007 no encaja en el
    contrato VectorStore, así que el pipeline recibe un `VideoStateStore`
    por constructor (mismo espíritu ADR-0007). repo.py (PR-007) no se amplía
    (fuera de allowed_paths): `PgVideoStateStore` reutiliza
    `PgRepo.connect()` con SQL propio dentro de indexing/.
  - **Cleanup en dos capas**: extract_frames (PR-008) ya garantiza el borrado
    por vídeo; el pipeline añade un dir de ejecución propio eliminado en
    finally — SC-006 verificable a nivel de pipeline incluso si una etapa
    futura creara temporales fuera del context manager.
  - **Errores controlados por vídeo**: cualquier excepción durante la
    indexación de un vídeo → `failed` con mensaje corto
    (`TipoError: mensaje`) y el dataset continúa. Si falla la marca de
    estado, el error original prevalece (raise exc from state_exc).
  - **Config validada en el constructor** (ValueError temprano) para
    frames_per_video/batch_size/dedupe_threshold/scale_width.
  - **pHash NO se persiste todavía**: el contrato `FrameRecord` (contracts
    §2, vectorstore/base.py — fuera de allowed_paths) no transporta el pHash
    y PgVectorStore inserta un centinela (0) con nota "hasta PR-010/013".
    El pipeline calcula pHash dentro del dedupe (PR-009) pero no puede
    persistirlo sin ampliar el contrato; ver Limitaciones.

- **Limitaciones**:
  - **pHash no persistido (gap de contrato)**: `FrameRecord` no transporta
    el pHash (vectorstore/base.py fuera de allowed_paths) y PgVectorStore
    inserta el centinela 0 (nota en pgvector.py: "hasta PR-010/013"). Para
    cumplir FR-004/FR-006 por completo hay que ampliar el contrato
    (añadir `phash` a FrameRecord y al INSERT de PgVectorStore, y opcional
    `width`/`height`) — requiere tarea con allowed_paths sobre
    vectorstore/**. Recomendación: PR pequeño antes del benchmark.
  - `PgVideoStateStore` asume el esquema PR-006 (columnas status,
    frame_count, duration_ms, error, indexed_at); su SQL no está cubierto por
    pgTAP (sí por el test 14 cuando hay DB).
  - La idempotencia de Pg depende de que el upsert use la misma clave de
    conflicto (frame_seq) que los ids generados; documentado y testeado en
    memoria, no contra DB (la paridad la garantiza el test de PR-007).
- **Riesgos**:
  - El pipeline atrapa `Exception` por vídeo: un error sistémico (p. ej. DB
    caída) marcaría todos los vídeos como `failed` en lugar de abortar;
    aceptado para la CLI del spike (el reporte lo hace visible), revisable en
    PR-011.
  - Duración de los tests: ~10 s por la generación FFmpeg de fixtures;
    aceptable en la suite (16 s totales).
  - Los conteos exactos de dedupe sobre testsrc2 no se asertan (dependen de
    imagehash); los tests asertan invariantes (0 < frames ≤ config, igualdad
    entre ejecuciones) — robustos ante cambios de librería.
